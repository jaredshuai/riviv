# riviv

Unofficial Rust rewrite of [voidtools/voidImageViewer](https://github.com/voidtools/voidImageViewer) (MIT) — a lightweight, single-executable image viewer for Windows.

Based on voidImageViewer by David Carpenter / voidtools. See [LICENSE](LICENSE). The original C implementation is preserved under [`c-original/`](c-original/) as a read-only behavioral reference.

> **Status: early development (M6 planned).** Current scope: Win32 window + GDI rendering, animated GIF/WebP playback at author timing, alpha-composited transparency for every supported format (PNG, JPEG, BMP, ICO, TIFF, GIF and WebP), drag & drop, a keyboard-navigable playlist, zoom/pan over the upstream 16-level preset curve, the settings foundation (the window rect is remembered across runs in a `[riviv]` ini with upstream's 60% first-run auto-fit), en/zh-CN localization driven by the system UI language, single-instance command-line forwarding (a second launch hands its image to the running viewer and exits), a menu bar over a command table (File/View/Navigate/Help carrying the implemented commands, toggled by `show_menu`), the Options dialog (General/View/Controls pages over the same ini — filters, fit/fill, auto-size, background colors, frame-minus, mouse actions, multiple instances, appdata location, start-menu shortcuts and file associations; OK applies live and saves), custom keyboard shortcuts (per-command bindings over the same ini — upstream's `*_keys` lines — editable on the Controls page; the keyboard route and the menu accelerator labels follow the live table), and the install family (the `/install`-family CLI, an embedded app icon, and an NSIS installer), and the Everything IPC search (Ctrl+E / Ctrl+Shift+E open a hand-built Search Everything dialog; the query goes out as a QUERY2 WM_COPYDATA to a running Everything, the LIST2 results fill the playlist — Open replaces, Add appends — and the Randomize checkbox arms an endless one-image-at-a-time mode bound to next/prev/home), and the slideshow (#37: F11 or View→Slideshow auto-enters fullscreen and advances the playlist on a timer; the Slideshow menu carries Play/Pause, the 17 rate presets and a Custom dialog; Space/↑/↓ and Esc follow upstream), and the view-frame family (#46: the Minimal/Compact/Normal presets, window sizing at 50/100/200%/Auto Fit, the always-on-top trio, F5 refresh and the View fit/shrink rows over the same frame rebuild), and embedded-ICC→sRGB color management (#77: the `icm` key applies a WCS transform to each frame at decode, before compositing). M3, M4 and M5 are feature-complete (M4 landed as #37–#50; M5 as #65–#69 — the `stdin:` pseudo-file, the clipboard image family, the `/close` slideshow switch, the `keep_zoom` carry and the one-seam shell-execute convergence); M6 (the rendering-stack & color-management pass — a D2D viewport over a WCS color pipeline, per ADR 0002) is ticketed as #76–#82 plus #90 (the GDI render-path removal split out of #82); see [Roadmap](#roadmap).

## Build

Requires the Rust toolchain with the MSVC target.

```text
cargo build --release
```

The NSIS installer (optional; needs NSIS 3, e.g. `winget install NSIS.NSIS`):

```text
installer/build-installer.ps1              # zh-CN installer (upstream default)
installer/build-installer.ps1 -Lang English
```

## Usage

```text
riviv.exe <image path>    open an image
riviv.exe <folder>        build a playlist from the folder (recursive) and open the newest image
riviv.exe <a.png> <b.png> build a playlist from the arguments and open the first
riviv.exe                 empty window; press Ctrl+O to pick a file
```

Install-family switches (upstream semantics; the process exits without a window after handling them): `riviv.exe /png` associates an extension (`/no<ext>` removes it), `/appdata` / `/noappdata` switch the settings location, `/startmenu` / `/nostartmenu` manage the all-users start-menu shortcuts, and `-install <dir>` / `-uninstall [dir]` (used by the installer) copy or remove the program. The elevated work re-executes itself via UAC when needed.

Drag & drop works the same way (upstream `WM_DROPFILES` semantics): a single dropped file replaces the current image; dropping a folder, multiple files, or holding Shift builds/extends the playlist (Shift appends instead of replacing). Navigate with Right/PgDn (next), Left/PgUp (previous), Home/End (first/last) — by the configured sort (Navigate→Sort: name / full path / size / date modified / date created, each ascending or descending; the shipped default is date modified, newest first). Navigate→Shuffle walks a random order instead, and J (Navigate→Jump To...) opens a searchable list of the navigable images. With no playlist, navigation walks the current image's folder.

Zoom & pan (upstream preset semantics): the mouse wheel and `+`/`-` step through the 16-level zoom curve (level 0 = fit, top level = 1600%) anchored at the cursor; drag with the left button to pan while the image exceeds the window; Ctrl+0 returns to fit; Ctrl+Alt+0 toggles a temporary pixel-exact 1:1 view.

Fullscreen (upstream semantics): double-click or Alt+Enter toggles a borderless cover of the current monitor (Esc also leaves it) — the pre-toggle window rect (and its maximized state) is restored on exit, the status bar is hidden for the cover, and an idle cursor hides after 2 s, reappearing on any movement.

Slideshow (upstream semantics): F11 or View→Slideshow starts a fullscreen auto-advancing playlist run; Space toggles pause/resume, ↑/↓ step the rate through the 17-preset ladder (250 ms … 60 s), the Slideshow menu picks a preset or opens the Custom dialog (value + ms/s/min unit), manual navigation re-arms the timer, and Esc both leaves fullscreen and pauses the run. With `loop_animations_once` on (the default), the advance holds until the current animation has played through once. While the run is up the status bar's main part reads "Slideshow playing" (windowed runs only — the fullscreen cover has no status bar, and the Loading/File-not-found/Failed verdicts outrank it) and the process holds the display awake (`prevent_sleep`).

Animation controls (upstream semantics): Ctrl+Space pauses/resumes the current animation (its menu check reads the playing state), Ctrl+PgDn/PgUp jump forward/backward by `medium_jump` (1000 ms default) of raw frame delay — the jump size is time, not frames; `short_jump`/`long_jump` variants are command-table-only (upstream hides them from the menu bar behind MF_OWNERDRAW, so in riviv they carry no menu row but stay bindable on the Controls page) — Ctrl+Right/Left step one frame, Ctrl+Home/End go to the first/last frame, and Ctrl+↓/↑/R walk the 21-step rate table (0.125×…8×, scaling every frame delay; Reset returns to 1×). The frame-step family pauses playback (even on a static image, where it only flips the state); jumps do not. The rate position persists across images; the pause resets on every open. Left-click action 2 (Options → Controls) toggles the animation pause. Every rate change flashes the status-bar readout for 3 s (#47).

Giant images (upstream semantics, reshaped by #81 and #82): the #9 mipmap pre-generation and per-render level selection are retired — the GDI arm renders shrinks from the single full-resolution frame face (upstream selected a mip level, viv.c:4167), stretches whose extents reach ≥ 32768 px take upstream's own no-mip shape (one full-rect StretchBlt behind a simple clip region, viv.c:4264-4283), and a SOURCE extent past 2^22 — where GDI stops stretching the face at all (sliced calls included past 2^23-wide faces; only 512-px slices read them, the #81 smoke census) — renders through a transient per-paint "relief" intermediate (a ~2^21 DIB, at most 2^21+1, rebuilt from the face in upstream's own 512-px generation tiling, then one blit from it). The D2D arm owns giants itself since #82 (no GDI hand-off): a frame past the runtime `GetMaximumBitmapSize()` picks a source LEVEL and a form per paint — a level that fits the device is drawn as ONE bitmap (level 0 is the ordinary path; a deeper level is the overview a giant shrinks through, a CPU box-downscale cached per frame+level), and a level that does NOT fit is cut into 1024-px tiles covering only the visible region's preimage (LRU-cached, byte-capped, each tile carrying a 32-px filter halo and clipped to its logical interior), so a giant at 1:1 keeps whole-screen source residency at O(viewport) instead of O(image). `-tile <edge>` forces the grid edge for diagnostics (`-dump-viewport`'s sibling; not a user-facing key).

Clipboard (upstream semantics): Cut (Ctrl+X) / Copy (Ctrl+C) put the current file on the clipboard as a file drop (CF_HDROP) with a `Preferred DropEffect` value (MOVE for Cut, COPY|LINK for Copy) plus the displayed frame's pixels (CF_BITMAP); Edit→Copy Filename (Ctrl+Shift+C) copies the full path as text (CF_UNICODETEXT); Paste (Ctrl+V) applies a clipboard file list exactly like a drop (a single file opens, a multi-file or Shift-drop builds the playlist — the CF_DIB image paste of the upstream wish list is not implemented). With no current file, or after a not-found/failed load, the Cut/Copy/Copy Filename/Copy Image commands gray out; during loading they remain usable (the file is already current — upstream's gate, viv.c:7101); Paste stays usable and ignores an empty clipboard (a malformed foreign file list is ignored the same way).

Shell verbs (upstream semantics, #42): File→Open File Location (Ctrl+Return) selects the current file in an Explorer window; Print (Ctrl+P), Edit, Preview and Properties hand the file to its registered shell verb handlers (exactly the verbs an Explorer right-click resolves — whether a verb exists depends on the machine's file associations, and a missing verb is a silent no-op like upstream); Set Desktop Wallpaper applies the current image behind the shell's `setdesktopwallpaper` verb; Close (Ctrl+W) blanks the display back to an empty window without exiting. All seven gray out with no current file or after a not-found/failed load (upstream's `is_image_enabled` gate).

File management (upstream semantics, #43): F2 (File→Rename) opens a rename dialog prefilled with the extension-stripped filename — OK renames through the shell (`FO_RENAME` with undo), adopting the collision-resolved name ("xxx - Copy") when the shell supplies one, and answering No at a collision keeps the dialog open for another try; the old extension is always re-appended, so typing a name with a dot gives a double extension (upstream quirk). Del sends the current file to the Recycle Bin and Shift+Del deletes it permanently (the shell's own confirmation dialog appears either way); the visible File→Delete row decides recycle vs permanent by whether Shift is held at click time. After a delete the viewer converges the playlist and navigates to the next image, blanking when nothing is left. Edit→Rotate Clockwise / Counterclockwise rewrite the file through the shell's `rotate90`/`rotate270` verbs (the OS photo handler owns the re-encode) and rotate the on-screen frames to match — including every frame of an animation, once decoding has finished (a no-op mid-stream, upstream's own wait gate). Edit→Copy to Folder... / Move to Folder... open a save-style dialog prefilled with the current filename (overwrite prompt included) and run the shell copy/move with undo. The six visible rows gray out like the shell family; the two explicit delete rows stay menu-hidden (keyboard + Controls page, upstream's MF_OWNERDRAW).

## Differences from upstream (intentional)

- The settings live in a `riviv.ini` with a `[riviv]` section next to the exe (or `%APPDATA%\riviv\` once switched) — upstream's `voidImageViewer.ini`; the namespaces are separate so both viewers coexist on one machine. The first run centers a 60%-of-monitor window on the cursor's monitor in that monitor's own coordinate frame, exactly like upstream (including the secondary-monitor quirk where the relative rect is re-anchored onto the window's monitor — viv.c:5383-5406); later runs restore the remembered rect/maximized state, saved on exit.
- The DEFAULT fit never upscales past 100% (upstream `fill_window=0`; `keep_aspect_ratio`/`fill_window`/`fullscreen_fill_window` are configurable in Options since #24, matching upstream semantics including the fill-mode zoom ladder).
- The window never resizes when switching images via drag & drop (upstream behavior).
- File associations and the install family (#26) live in riviv's own namespace: progids `riviv.<ext>` under `HKCU\SOFTWARE\Classes` (backup value `riviv.Backup`, upstream's is `voidImageViewer.Backup`) and a `riviv` folder for the all-users start-menu shortcuts — so both viewers' associations coexist and each uninstalls only its own. Uninstall removes the progid with `RegDeleteTreeW` where upstream calls the single-level `RegDeleteKey` — which FAILS on a key with subkeys (a progid always has DefaultIcon + shell\open\command), so upstream silently leaks the whole progid tree on every uninstall; riviv cleans up fully instead (the issue's "no residue after uninstall"). The `-install` copy skips upstream's `Changes.txt` (riviv ships none). The NSIS installer (`installer/nsis/riviv.nsi`, build with `installer/build-installer.ps1`) is a port of upstream's script onto MUI2 (upstream ships MUI v1) and keeps upstream's trick of staying `RequestExecutionLevel user` — the staged exe's own `/install` pass elevates via its `runas` re-execution.
- Animated WebP frames shorter than 10 ms play quantized to the `USER_TIMER_MINIMUM` timer period — a two-frame 5 ms animation advances two frames per tick and can appear frozen. Upstream's primary path additionally drives a 1 ms timer-queue timer (`CreateTimerQueueTimer`, viv.c:9132-9141) for those; GIF delays are 10 ms multiples and never hit this.
- The Animation jump walk floors each consumed frame delay at 1 ms (#38): upstream's `_viv_frame_skip` subtracts raw delays, so a run of zero-delay frames (possible in WebP; the GIF loader floors to 100 ms) spends no budget and would loop forever — riviv's walk terminates at one millisecond per frame. Only the zero-delay corner differs; every real delay passes through untouched.
- A user-level load failure (bad path, undecodable file, decode-budget overflow) never pops up or exits. The window title adopts the requested file at REQUEST time (upstream viv.c:1574-1578) and a failure never reverts it. Before the first frame, the old image stays on screen (upstream blanks here) while the title bar already carries the failed file's name; once the new image's first frame is already on screen, a later failure of that same load (e.g. a budget overflow mid-animation) cannot roll the old image back and clears to a blank window instead, the title keeping the failed file's name — like upstream's async FAILED handler, which clears the frame data only (viv.c:2832-2840; only blank clears the title too, viv.c:7919-7923). The same family covers navigating to a file deleted after the playlist was built: riviv's pre-open check shows "File not found." (upstream would show "Failed to load image." after blanking).
- The decoded frame's source of truth is a pure-memory CPU frame (#76, [ADR 0002](docs/adr/0002-d2d-wcs-render-stack.md) D3): the background decode produces no GDI object at all, and the GDI face (DIB section + memory DC) is derived on the UI thread at the frame's FIRST paint — after the reply drain has adopted the image and run the window auto-size, so a huge frame's build cost lands inside the paint that consumes it. Three visible-adjacent consequences: a face-build failure (GDI exhaustion) degrades to a blank frame at paint time instead of upstream's worker-side allocation surfacing through the load-reply path (never a fatal modal; a stderr breadcrumb is left, the frame never retries); the in-memory rotation (#43) has no GDI failure arm — the master always turns, and a face failure shows the turned frame blank rather than keeping the old orientation; and the decode of the frames AFTER a foreground animation's first frame waits for that first frame's paint (a bounded handshake — 50 ms terminate polls, a 5 s cap for a minimized window; preloads and stills never wait) — translating the serialization upstream's worker got for free from building each frame's GDI objects between replies, without which a mid-stream failure (the decode budget) could clear the partial display before its first frame ever renders.
- Mipmap-chain failures (a #9–#80 behavior, retired with #81 — see the #81 bullet) degraded to a shallower level (or the original) and kept rendering; upstream propagates a `NULL` level into not drawing the image at all (viv.c:14226→4167-4169). While the chain existed, its objects were capped by a process-wide GDI-object budget (upstream had none — unbounded chain growth under the old fail-loud allocation path made the 10000-object process quota a crash otherwise), the pre-generation share kept upstream's truncation contract and a render-depth failure stuck for the surface's lifetime (review PR #18's no-retry-storm rule), per-tile StretchBlt failures kept stitching the remaining tiles (upstream aborts the rest on the first failure, viv.c:14999-15002), and degenerate zero-area tiles were skipped rather than handed to GDI.
- A giant-extent HALFTONE shrink (dest or source ≥ 32768 px — the source is the full-resolution face since #81, so this covers any ≥32768-source shrink) wraps the full-rect StretchBlt in a single simple clip region = the update paint rect intersected with the viewport. Upstream iterates the update region's rects one by one (viv.c:4262-4284); riviv's coarser clip redraws the update bounding box on every WM_PAINT instead of each exact dirty rect. Non-giant shrinks keep the #7 single full-rect blt (pixel-identical to upstream's per-rect loop, performance-only difference on complex update regions).
- Magnified rendering re-anchors the source sub-rect (`clip_blit`) instead of upstream's full-rect-accurate `_viv_stretch_blt`/stitched stretch — up to ±1 source pixel of sampling phase on very high zooms, and the visible region is re-stretched every paint rather than only the dirty rect's source area (inherited from the #7 zoom work). Since #81 this deviation is GDI-arm-only: on the D2D arm the magnify is expressed by the exact destination rectangle (no re-anchoring, no ±1px phase), while the GDI escape arm (`renderer=gdi` or a D2D init/session degrade — an oversized frame no longer leaves the D2D arm, see the #82 bullet) keeps `clip_blit`.
- The status bar (#47) follows upstream's full `_viv_status_update` contract: the main text (Loading / File not found. / Failed to load image. / Slideshow playing), the temp-text flash line (the position/zoom readout on every panscan command, the animation-rate and slideshow-rate readouts — each landing for 3 s then falling back), the dynamic preload indicator (#40), the POS / RGB pixel-info parts (on with `statusbar_pixel_info`, ini-only like upstream — the source-pixel coordinate under the cursor and the color read directly from the displayed frame's CPU master (the GDI face derives from the same bytes, #76; upstream builds a scratch DC and GetPixels the displayed bitmap — identical values, no GDI roundtrip), resampled on every mouse move and every frame change), the frame counter (the status-bar click toggles the frames-remaining form, upstream's NM_CLICK-on-part-1 — with the part order `[main][preload?][pos][rgb][frame][dimension]` part 1 is the POS readout when pixel-info is on and a zero-width dead slot when off, upstream's hardcoded index kept bug-for-bug), and the `W x H (N KB)` dimensions. The POS/RGB parts always exist in the SB_SETPARTS layout (upstream's part-array guards test the array pointer, always true) — zero-width and invisible until their text shows. Two deviations: the frame counter's `m` counts the *loaded* prefix and grows while an animation streams in — image frame iterators cannot report the total up front (GDI+/libwebp can), so the click-toggled frames-remaining form counts down within it too; and the temp-text formatting recomposes the localized labels around the same number slots (byte-identical strings, including the f32 rounding asymmetries of upstream's C expressions).
- The toolbar (#45) keeps upstream's geometry and semantics — a 32-DPI-scaled strip docked above the status bar with the six labeled buttons (Previous Image / Next Image / Play Slideshow / Pause Slideshow / Best Fit / Actual Size; play/pause a check-group mirroring the slideshow state, Best Fit / 1:1 graying at the state they would enter, the minimum track width following the toolbar's measured width, and the strip/menu-bar-empty-area/status-part-0 drags moving the window under the default-on `toolbar_move_window` ini) — with three divergences: the button glyphs are drawn at runtime at the DPI-scaled size instead of upstream's rc icons (the c-original archive ships no rc; same slots, riviv-authored shapes), the two toolbar-only slideshow commands (`VIV_ID_SLIDESHOW_PLAY_ONLY`/`PAUSE_ONLY`) are registered as hidden command-table rows where upstream keeps them out of the table entirely — so in riviv they additionally appear on the Controls page and carry `*_keys` ini lines (a superset, not a behavior change), and panscan commands still do NOT refresh the button states (upstream's own gap: its panscan handlers never pass through `_viv_view_set`'s toolbar refresh; kept bug-for-bug).
- The view-frame family (#46) follows upstream's `_viv_update_frame` contract: the five chrome toggles (Menu / Status Bar / Controls plus the hidden Caption / Frame style-bit rows — MF_OWNERDRAW upstream, so ini/custom-binding reachable like the #38 jump family), the Minimal/Compact/Normal presets, the Window Size quartet (50/100/200%/Auto Fit over #24's sizing engine), Refresh (F5 — clears the last/preload caches, blanks keeping the current file's title, re-reads from disk), the Allow Shrinking / Keep Aspect Ratio / Fill Window rows (Fill reads the current mode's fill config, upstream's own quirk) and the On Top trio (Always is a TOGGLE whose C `!` collapses the while-playing value 2 onto never — kept bug-for-bug) all funnel through one frame rebuild that keeps the VIEWPORT stationary; fullscreen flips the configs but defers the rebuild to the exit (upstream's early return). Two divergences: `ontop=2` ("while playing or animating") re-evaluates the topmost bit at every animation play/pause and animation-timer transition — upstream re-evaluates only on slideshow start/pause and menu opens, so a paused animation left its topmost state stale until one of those; and the `/ontop` `/minimal` `/compact` CLI switches act through the same command handlers (upstream fidelity, landing here after #48 had recognized them inert).
- The shell verb family (#42) rides upstream's `os_shell_execute` exactly: the file is resolved to a shell item id list (`ILCreateFromPath`) and invoked with `SEE_MASK_INVOKEIDLIST`, so every verb — including "properties" and "setdesktopwallpaper" — resolves through the item's context-menu handlers like an Explorer right-click (a raw `lpFile` launch would miss several of them). Open File Location keeps upstream's `SHOpenFolderAndSelectItems` path with the E_ABORT≈success quirk and the open-the-folder fallback; Wallpaper keeps the one-shot `stobject.dll` LoadLibrary gate (no execute when the load fails, no dialog either — fail-soft like upstream); Close IS upstream's `_viv_blank` port (the shared blank path: title/status/pixel/playlist all reset, the slideshow timer state kept running). The File→Edit row and Wallpaper stay keyless like upstream (Ctrl+E belongs to the Everything search; wallpaper "needs a confirmation dialog", viv.c:979/982 — both bindable on the Controls page all the same). One deviation: the location handler's parent-folder slice uses `Path::parent`, so a root-level file's parent stays `C:\` — upstream's separator-slice produces the bare `C:` (the per-drive CURRENT directory, not the root; upstream quirk, not reproduced).
- The file-management family (#43): Delete (recycle/permanent via the visible row's live Shift probe, Del / Shift+Del on the two menu-hidden rows) and Rename go through `SHFileOperation` exactly like upstream — the shell's own confirmation/collision dialogs, undo info (`FOF_ALLOWUNDO`), and the rename dialog adopts the shell's collision-resolved name through `hNameMappings` (the documented HANDLETOMAPPINGS shape upstream reads). Upstream quirks kept: the rename composer unconditionally re-appends the old extension (typing `foo.png` renaming `a.png` lands `foo.png.png`) and `string_get_extension` scans the WHOLE path (a dot in a directory name leaks into the "extension"); a Move To leaves the display, the current file reference and the playlist pointing at the moved-away path until the next navigation slides off (upstream syncs only Rename and Delete); the last-image cache keeps the pre-rename path (upstream renames only `current_fd`). One implementation deviation from the ticket's literal step list: the RGBA→BGRA swizzle is folded INTO `TranslateBitmapBits`' output format (`BM_xRGBQUADS` = the master's `[B,G,R,x]` layout) so the composite runs on the BGRA output directly — semantically identical to the ticket's "composite, then swizzle" order and one full-buffer pass cheaper; the transform restores each pixel's source alpha itself, because the `x` byte of the `BM_x*QUADS` formats is documented *unused* and the composite's blend keys on it. The sRGB-equivalence call is a heuristic, not a proof: the probe compares a 1024-pixel ramp through the built transform and calls anything within an 8/255 max-channel drift equivalent — an octave above the observed ≤4/255 CMM noise floor, an order of magnitude below a real foreign profile's midtone movement — so a borderline profile inside that band can land either way. Conversion results can still differ from GDI+'s CMM in the last LSB — a transform-engine difference, not a pipeline one. Stage 1 deliberately stops at the device-independent sRGB master: per-display output profiles, profile hot-reload and HDR/WCG-aware output are Stage 2 (see Unscheduled).

Backend visibility: every launch prints `riviv: renderer=<request> backend=<effective>` on stderr, and since #82 every D2D stack build additionally prints `riviv: d2d max_bitmap=<n> tile cap=<n> (dxgi budget=<n|unavailable>)`, About names the effective renderer, and the status bar's dimension part gains a ` d2d/hw` / ` d2d/warp` suffix ONLY while a D2D stack actually renders — `gdi` stays suffix-free, so the pre-#81 default launch kept upstream's status bar byte-identical (the `auto` default since #81 shows the suffix; `renderer=gdi` still hides it). The renderer key is ini-only (no Options UI in #80). Two deliberate widenings of the failure ladder beyond the documented loss codes (pre-review filed): ANY `EndDraw` failure — not just `D2DERR_RECREATE_TARGET` — enters the same rebuild ladder (a rebuild is cheaper than painting on a sick device, and the 3-in-10s window bounds the churn; the terminal tier is the deferred fatal, never a GDI hop, so a hypothetically persistent non-loss EndDraw error would end as a 10-second exit rather than a silent GDI degrade), and an oversized ANIMATED image (a giant GIF) used to bump `frame_gen` per frame and rebuild the torn-down stack once each — a #80-era transitional pathology that #82's own giant path removed outright (a giant frame no longer tears the stack down at all). Finally the automation channel: `-dump-viewport <path>` (both `/` and `-` spellings, sticky like `/close` — a single-instance handoff arms the FIRST instance too) renders the CURRENT viewport scene at WM_CLOSE — before the teardown, after the script has orchestrated 1:1/zoom/rotate/fullscreen — and writes a PNG; both the D2D arm (render into the target, no Present, read back through a CPU-readable bitmap) and the GDI arm (the same scene into a memory-DC DIB) dump independent of window visibility, so a never-shown background window still dumps; failures are stderr + exit code 2, never a modal (that exit skips the ini save by construction — it fires before WM_DESTROY, the automation channel's documented trade). The dump rides WM_CLOSE, File→Exit, and the `/close` slideshow tail alike; the one bypass is WM_ENDSESSION (no dump attempt during system shutdown — a shutdown must not wait on a PNG). A handoff-armed dump (`-dump-viewport` forwarded to the first instance) resolves relative paths in the FIRST instance's working directory — scripts should pass absolute paths. And one latch to know: a renderer init failure (or a rebuild failure after device loss) latches to GDI for the process lifetime — a driver that recovers mid-session needs a restart before D2D comes back (the latch exists to keep a broken environment from retrying the device on every paint). Two scoping honesties for the "renderer=gdi is zero-difference" claim (external review AI2): it means zero RENDERING difference — such a launch also gains the one stderr breadcrumb line, the About renderer line, and one `renderer=<requested>` key in the saved ini (none of which the upstream surface ever reads; the saved key is the REQUESTED value — a mid-session degrade never rewrites it, so `renderer=auto` stays `auto` even on a machine whose stack fell back to GDI); and the exe's import table statically binds `d3d11.dll`/`d2d1.dll` (OS components present since Win8, so a 1607+ machine cannot miss them) — "init failure degrades to GDI" therefore covers device CREATION failures, not loader failures. The failure classification is a shared table (external review AI2 P1): the documented loss codes plus `DRIVER_INTERNAL_ERROR` take the rebuild ladder; any OTHER EndDraw/Present failure is deterministic trouble a rebuild cannot fix and degrades the whole session to GDI (teardown + one-shot flash + a queued repaint — never a frozen frame, never a wrong fatal). The #80 scope drew the shrink Linear tier as plain BILINEAR — visibly softer than GDI's HALFTONE on strong downscales; #81's full filter table (HIGH_QUALITY_CUBIC per ADR 0002 D6) closed that quality gap (see the #81 bullet).
- The filter table and the mip retirement (#81, [ADR 0002](docs/adr/0002-d2d-wcs-render-stack.md) D6/D7). Filters, D2D arm: the ini's two two-tier keys (`shrink_blit_mode`/`mag_filter`, 0 = Nearest, 1 = Linear) map onto the full `D2D1_INTERPOLATION_MODE` table — 1:1 stays NEAREST pixel-exact unconditionally, a shrink at Linear draws HIGH_QUALITY_CUBIC, a magnify at Linear draws LINEAR, and every 0 tier draws NEAREST — so the 0 tiers and 1:1 are unchanged, and the shrink Linear tier is deliberately BETTER than the GDI arm's HALFTONE (a prefiltered cubic against HALFTONE's directional aliasing on strong downscales; the ini tier's user-visible name stays "Linear"). Mips, retired: upstream selects a cached downsampled level for every zoomed-out paint (`_viv_get_mipmap`, viv.c:4167) — riviv's GDI arm now stretches every shrink from the single full-resolution face, so GDI-arm shrink pixels deliberately diverge from upstream's (a filtered full-res sample beats GDI HALFTONE against a small mip's blocky upscale, and the D2D arm never had mips); the mip-selection quirk (render height compared against level width, viv.c:14181) and the HALFTONE `SetBrushOrgEx` dither-anchor parity (viv.c:4205-4209) are dropped with it — with the chain gone and no dithering on a 32bpp→32bpp StretchBlt, neither is observable anymore, and replicating them would be deliberately worse output. Of the pure math, #82's giant tiering reuses `mip::mip_size` (level dimensions) and the newly added `mip::downscale_box` (the overview build); `mip::select_mip_level`'s upstream quirk parity and `stitch::stitch_tiles` stay as the historical record and their own regression nets — the tiling shares their projection DISCIPLINE (one destination edge per shared source coordinate) but is a separate windowed implementation (see the #82 bullet). Giant images on the GDI arm keep upstream's own no-mip shape: with the chain retired, ANY shrink whose source extent reaches 32768 goes through one full-rect StretchBlt behind a simple clip region (viv.c:4264-4283) — the tall-narrow cases upstream always hit, not a new behavior class. One regime upstream never reaches (its mip chain keeps paint sources small) needed new behavior: past a 2^22-wide/tall face GDI stops stretching it AT ALL — the classic giant-panorama black image, mapped by the #81 smoke census (4,000,000- and 6,291,456-wide faces render, 8,388,608-wide ones go black even for wide slice calls; only 512-px slices keep reading them, exactly the tiling upstream's own mip generation used) — so those paints build a transient relief intermediate per paint: a ~2^21 DIB (at most 2^21+1) filled from the face through upstream's 512-px HALFTONE generation tiling — note the relief pass is HALFTONE whatever the ini tier, so in this extreme band even the shrink "Nearest" tier's output is a HALFTONE prefilter away from point-sampled (upstream's own mip generation had the same property), and the band's reachable shapes under the 512 MB frame cap are extreme-aspect stripes only — then the scene's single blit runs from it (no chain, no cache — the escape-arm transition until #82's D2D tiling owns giants; 2^21 sliced blits remain as the allocation-failure degrade). The relief guards the SHRINK arm only. A ≥2^22-axis face can still legally reach the magnify arm (the preset curve renders up to 16x the source), where the two mag tiers expose differently: `mag_filter=1` blits the full uncut rect — the whole giant face in one call, the census-proven failing shape, deterministic black; `mag_filter=0` (the default) cuts to the viewport and the cut's source sub-rect is viewport-bounded (a few thousand px, never near the trigger), landing in the unverified census band on ≥2^23 faces (proven good ≤512-px slices, proven bad at 2^21) — may render or black. An upstream-shared latent defect on an escape-arm corner, documented here rather than patched into the GDI escape arm — #82 scoped it out with the rest of the GDI deletion, so it now rides #90 (retiring the arm and the constant with it). And the default renderer is `auto` since this issue (hardware D2D → WARP → GDI transitional ladder, ADR 0002 D5): `renderer=gdi` is the explicit escape back to the byte-for-byte GDI baseline — note for migration honesty that every ini saved by a #80-era build already carries a literal `renderer=gdi` (the save always writes the current value), so the flip reaches fresh and keyless inis only, never a #80-saved one.

- The giant-image path on the D2D arm (#82, [ADR 0002](docs/adr/0002-d2d-wcs-render-stack.md) D7). A frame past the runtime `GetMaximumBitmapSize()` no longer leaves the stack: per paint it picks a source LEVEL (`tile::detail_level` — level 0 for 1:1/magnify, else the deepest mip level whose dimensions still cover the render, i.e. a prefiltered source that is never magnified) and then a FORM — a level that fits the device is ONE bitmap (level 0 = the ordinary path, deeper = the overview, built on the CPU by `mip::downscale_box`: one from-original pass, integer block boundaries that cover every source pixel exactly, no premultiply needed because the master is opaque by construction — a different prefilter from upstream's GDI-HALFTONE mip generation, which is gone with the chain); a level that does NOT fit is cut into 1024-px tiles (`-tile <edge>`, both `/` and `-` spellings like every switch, forces the edge for diagnostics; unlike `-dump-viewport` it is NOT sticky — a later command line without it restores the natural decision), each covering only the visible region's preimage, haloed by 32 source px for the filter taps and clipped to its logical interior. Measured, same image and transform, tiled vs untiled: **at 1:1 the two dump files are byte-identical** (asserted by `smoke82` S2a as whole-file hash equality — NEAREST plus integer rects plus one shared i64 projection, the five-piece contract intact), and **at a fractional scale (the filtered tiers) there is no structural seam**: the largest column-to-column step within 2 px of each tile boundary is the same as the untiled reference's (measured 0.299 vs 0.299 on a smooth ramp). The pixel difference there is bounded but NOT zero, and the honest statement is per content: on a smooth field every differing pixel is ±1 per channel (~10 % of them, mean absolute difference 0.035), while on high-contrast content a sub-pixel resampler-phase difference can move an edge pixel by up to 21 (the same measurement, on a hard-edged fixture) — the same phenomenon, not a displacement. That distinction is not cosmetic: an integer-truncated tile draw rect (the first cut) drifts each tile's implied scale (measured: 19 % of a shrink's pixels off by ±1), hence sub-pixel draw rects (`src_to_dest_f`, f64 → one f32 rounding) against integer CLIP rects (which must stay integer: they are what partitions the destination exactly); and the 32-px halo is an EMPIRICAL constant pinned by `smoke82` S2b — 8 px let a 0.65× shrink's taps reach off the bitmap into clamped pixels (up to 37 per channel at the boundary columns). A scale-derived variant (`32 / scale`) was tried once during development and measured worse under S2b's configuration (max delta 1 → 21), which is why it did not ship; that trial is not reproducible from the repo and S2b is a forced level-0 deep shrink rather than the (0.5, 1] regime the constant is tuned for, so it establishes no general property of D2D (external review AI1 P2-2). Known residual, recorded rather than papered over: an anisotropic frame (one axis forcing level 0 while the other shrinks by more than ~2×) can out-run a 32-px margin on the shrinking axis — reachable only with per-axis panscan zoom on a > `GetMaximumBitmapSize()` source under a filtered tier, and visible as a 1-2 px shading at that axis's tile boundaries. The halo costs bitmap area only (a halo pixel is never an extra upload): at the shipping 1024-px edge the haloed bitmap is (1024+64)² ≈ 13 % larger than the interior it serves. Budget: `MIP_GDI_OBJECT_BUDGET` died with #81, so the cap is BYTES — a `tile::Lru` over the resident tile bitmaps plus the level bitmap, capped at `budget_cap(IDXGIAdapter3::QueryVideoMemoryInfo(LOCAL).Budget)` = a quarter of the driver's budget clamped into 16 MiB…256 MiB (the query needs the adapter to be an `IDXGIAdapter3`; without it the self-set 256 MiB stands — and on an integrated GPU the LOCAL segment is system memory, so the clamp is what keeps its large Budget from being read as free VRAM). Under pressure the ladder evicts the least-recently-used tiles, then COARSENS the level (a uniform quality drop — never a frame that is half sharp, half stale: the GPU budget is charged for the frame's whole working set, resident tiles included, and the upload pass marks every already-resident frame tile hot first, so an eviction can only reclaim non-frame entries), then falls back to the single overview bitmap; it never leaves the D2D arm. `-tile <edge>` (the diagnostic) bypasses the budget check as well as the single-bitmap shortcut, so a FORCED frame may deliberately run over budget and partially cover — that is the pressure probe, not a product mode. In a live D2D session an upload that still fails (creation error, a refused level after the ladder) letterboxes THAT frame — the session does not switch to GDI and does not fatal (ADR 0001's keep-the-old-image tier governs decodes; the render stack's own degrade is the EndDraw/Present ladder). Acceptance substitution, recorded: the design's 40000×40000 fixture is not loadable at all (6.4 GB against the decoder's 512 MB frame budget), so the giant coverage is the 40000×256 hardware banner (fit and 1:1) plus the 16777217×1 stripe (the deep-shrink overview and, at 1:1, the tile path) — `smoke82` S3/S4 — and the deep-shrink overview is exercised by the 40000×256 fit (`level=5`, a 1250×8 level bitmap). CPU levels are cached separately (128 MiB, keyed frame+level, dropped when the frame changes) and counted in the ledger's four byte classes — note the cost that buys: the first paint of a given (frame, level) pays one box-downscale pass over the master ON THE UI THREAD (measured in release, 2026-09-20: 4 ms for a 40000x256 banner's level 5, 131 ms for 8000x6000's level 1, 402 ms for the largest cacheable overview — 16389x8189's 128 MiB level 1; cached per frame afterwards, and counted as `mip_builds`), whose totals and peaks print as one close-time stderr line with thirteen fields (`riviv: tiles level=<L> tiles=<n> base=<b> gpu=<b> peak_gpu=<b> inflight=<b> peak_inflight=<b> uploads=<n> evictions=<n> mip_builds=<n> source=<b> display=<b> cap=<b>`) whenever the giant path ran (or a `-tile` diagnostic forced one) — the smoke's evidence channel. Risk honesty (external review AI2 P2-3): since #82 the D2D arm's giant failure chain is D2D-ONLY — the #80 gate's GDI hand-off is gone, so a prepare failure letterboxes that frame (no stack teardown, no GDI switch; see above), and the tile path is nearly unreachable on WARP (its `GetMaximumBitmapSize()` is 2^23, so only > 8-Mpx-per-axis frames tile there), which makes the empirical coverage hardware-and-this-machine single-arm — one more reason #90's environment matrix (RDP / Hyper-V / WARP) is a deletion criterion, not paperwork. Scope honesty: #82 shipped the giant path and the budget only — deleting the GDI render main line AND the golden-corpus freeze it needs (the corpus exists to outlive the GDI stack that generates it, so it has no consumer before the deletion) moved to #90 after the written criteria (`renderer=auto` initialising in every target environment, a frozen corpus, one stable release cycle) turned out to be two-thirds unmet at #82's start, so `renderer=gdi` and the GDI giant relief remain, and the relocation of that transition is #90's first job.
